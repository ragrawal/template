# ml Specification

## Purpose
Defines the Copier template source at `templates/ml/`, an additive overlay that generates a house-price ML training pipeline, a local-filesystem training task, a FastAPI serving app, and Docker packaging on top of a project already generated from `templates/python-project`.

## Requirements

### Requirement: Copier template source overlays a house-price ML pipeline onto an existing project
This repository MUST contain a second, independent Copier template source at `templates/ml/` (`copier.yml` plus templated content mapped directly onto a project root) that, when run via the Copier CLI against `templates/ml` with a destination that already contains a project generated from `templates/python-project`, adds `src/<package_name>/estimator.py`, `src/<package_name>/tasks/`, `webapp/`, and `docker/` into that existing project without recreating or overwriting files that already exist there (`pyproject.toml`'s packaging metadata, per-tool config files, `README.md`, `AGENTS.md`, `.gitignore`, `src/<package_name>/__init__.py`, `py.typed`).

#### Scenario: Overlay onto an existing python-project-generated project
- **WHEN** a developer runs the Copier CLI against `templates/python-project` into a destination `<dest>`, answering `package_name` and `python_version`, and then runs the Copier CLI against `templates/ml` with `<dest>/<package_name>` as the destination
- **THEN** `<dest>/<package_name>` contains `src/<package_name>/estimator.py`, `src/<package_name>/tasks/train_model.py`, `webapp/app.py`, `docker/Dockerfile`, and `docker/.dockerignore`, and every file the first run created (`pyproject.toml`, `ruff.toml`, `pyrightconfig.json`, `pytest.ini`, `.coveragerc`, `poe_tasks.toml`, `README.md`, `AGENTS.md`, `.gitignore`, `src/<package_name>/__init__.py`, `py.typed`) is unchanged in content

#### Scenario: package_name is derived from the destination, not prompted
- **WHEN** a developer runs the Copier CLI non-interactively against `templates/ml` with destination `<dest>/<package_name>` and supplies no `package_name` answer
- **THEN** generation succeeds and every rendered file resolves `package_name` to the destination directory's own name, with no prompt or error about a missing answer

#### Scenario: Destination directory name cannot be derived
- **WHEN** a developer runs the Copier CLI against `templates/ml` with a destination whose path resolves to an empty directory name (for example, running it with `.` as the destination argument)
- **THEN** generation fails with a non-zero exit and an error explaining that the expected files under `src/<package_name>/` were not generated because `package_name` could not be derived from the destination, and that the developer must either re-run Copier with an explicit destination directory name or supply `--data package_name=<name>`, and afterward none of the files or directories that `templates/ml` would have added remain in the destination

### Requirement: Overlay run fails clearly against a destination not generated by templates/python-project
Running the Copier CLI against `templates/ml` with a destination that lacks `.answers/.python_project.yml` (the marker written by a `templates/python-project` run) MUST fail with a clear, human-readable error identifying the missing prerequisite, rather than succeeding into a broken state or failing later with an unrelated error (such as a dependency-install failure with no explanation), and MUST leave the destination free of any files or directories that this template would otherwise have added.

#### Scenario: Overlay run rejects an unrelated or empty destination
- **WHEN** a developer runs the Copier CLI against `templates/ml` with a destination that does not contain `.answers/.python_project.yml`
- **THEN** the run exits with a non-zero status and an error message stating that `templates/ml` must be run against a destination already generated by `templates/python-project`

#### Scenario: Failed prerequisite check leaves no partially-generated files behind
- **WHEN** a developer runs the Copier CLI against `templates/ml` with a destination that does not contain `.answers/.python_project.yml`
- **THEN** after the run exits non-zero, none of the files or directories that `templates/ml` would have added (including `src/<package_name>/estimator.py`, `webapp/app.py`, `docker/Dockerfile`, and `.answers/.ml.yml`) remain in the destination

### Requirement: Generated project includes a house-price estimator
The generated project MUST include `src/<package_name>/estimator.py` defining an estimator with `fit`, `transform`, and `predict` methods that trains on and predicts from the California-housing-shaped feature set (median income, house age, average rooms, average bedrooms, population, average occupancy, latitude, longitude) used by the reference implementation.

#### Scenario: Estimator trains and predicts
- **WHEN** the estimator's `fit` method is called with feature data and target house values, followed by `predict` on held-out feature data
- **THEN** it returns a prediction for every input row, with no change in row count between input and output

### Requirement: Generated project trains and persists a model to the local filesystem
The generated project MUST include `src/<package_name>/tasks/train_model.py`, a task that loads training data from a bundled local dataset (no external database or cloud dependency), trains the estimator, evaluates it on a held-out split, and writes the trained model artifact to a local filesystem path.

#### Scenario: Training produces a local model artifact
- **WHEN** a developer runs the training task in a generated project with no network or cloud credentials available
- **THEN** the task completes successfully and a trained model artifact file exists at the configured local output path

### Requirement: Generated project serves predictions over HTTP
The generated project MUST include `webapp/app.py`, a FastAPI application that loads the trained model artifact and the estimator's classes from the local filesystem at startup, exposes a `GET /health` endpoint reporting readiness, and exposes a `POST /predict` endpoint that accepts feature records and returns a prediction per record.

#### Scenario: Health check before and after model load
- **WHEN** the FastAPI app has started and the configured model artifact path is readable
- **THEN** `GET /health` responds with a success status

#### Scenario: Predict endpoint returns one prediction per input record
- **WHEN** a client sends `POST /predict` with a list of feature records
- **THEN** the response contains exactly one prediction per submitted record, in the same order

### Requirement: Generated project is packaged for Docker deployment
The generated project MUST include `docker/Dockerfile` and `docker/.dockerignore`. Building the Dockerfile MUST produce an image that, when run, starts the FastAPI serving app with the trained model artifact and estimator code loaded, without requiring cloud credentials or external services at container start.

#### Scenario: Container serves predictions after build
- **WHEN** a developer builds the Docker image from `docker/Dockerfile` (with a trained model artifact present in the build context) and runs the resulting container
- **THEN** `GET /health` on the container's exposed port responds with a success status and `POST /predict` returns predictions

### Requirement: Overlay run adds ML runtime dependencies to the existing pyproject.toml
Running the Copier CLI against `templates/ml` MUST add `scikit-learn`, `pandas`, `numpy`, `pydantic`, `fastapi`, and `uvicorn` as runtime dependencies to the destination's existing `pyproject.toml` (and update its lockfile), without `templates/ml` shipping or overwriting a `pyproject.toml` of its own.

#### Scenario: Dependencies install cleanly for both training and serving
- **WHEN** a developer runs the Copier CLI against `templates/ml` on a destination already containing a `pyproject.toml` from `templates/python-project`, then runs `uv sync`
- **THEN** `pyproject.toml` declares `scikit-learn`, `pandas`, `numpy`, `pydantic`, `fastapi`, and `uvicorn`, and both the training task and the FastAPI app import successfully with no additional manual dependency installation

### Requirement: Overlay run tracks its own answers separately from the base template
The Copier CLI run against `templates/ml` MUST write its answers to `.answers/.ml.yml`, alongside (not instead of) the base template's own answers file, so it does not overwrite the answers file the `templates/python-project` run already wrote to the same destination.

#### Scenario: Base template's answers file is preserved
- **WHEN** a developer runs the Copier CLI against `templates/python-project` into `<dest>`, then runs it against `templates/ml` with `<dest>/<package_name>` as the destination
- **THEN** `<dest>/<package_name>/.answers/.python_project.yml` (written by the `templates/python-project` run) is unchanged, and `<dest>/<package_name>/.answers/.ml.yml` records the `templates/ml` run's own answers

### Requirement: Pydantic models are self-documenting via Field descriptions
Every Pydantic `BaseModel` field bundled by the `ml` overlay (in `schema.py` and in the webapp's request/response models in `webapp/app.py`) MUST be declared using `pydantic.Field` with a non-empty `description`, so the model's JSON schema documents each field without relying on external documentation. The generated project MUST include an automated check, run as part of its test suite (and therefore as part of `uv run poe check`), that fails if any of these bundled models declares a field without a `Field` description.

#### Scenario: Webapp request/response models declare Field descriptions
- **WHEN** a project is generated with the `ml` overlay
- **THEN** every field on `HealthResponse`, `HouseRecord`, `PredictRequest`, `Prediction`, and `PredictResponse` in `webapp/app.py` is declared via `Field(..., description=...)` with a non-empty description

#### Scenario: Missing field description fails the test suite
- **WHEN** a bundled Pydantic model's field is declared without a `Field` description (for example, during future maintenance of the template)
- **THEN** the generated project's test suite fails, identifying which model and field lacks a description

### Requirement: Generated project's ML test files mirror the source layout they exercise
The tests that `templates/ml` adds to a generated project MUST be organized so each test file's path mirrors the module it exercises: the tests for `src/<package_name>/estimator.py` and `src/<package_name>/schema.py` MUST live under `tests/<package_name>/`, the test for `src/<package_name>/tasks/train_model.py` MUST live under `tests/<package_name>/tasks/`, and the test for `webapp/app.py` MUST live under `tests/webapp/`.

#### Scenario: Test files land under package- and webapp-mirrored directories
- **WHEN** a developer overlays `templates/ml` onto a `templates/python-project`-generated destination
- **THEN** `tests/<package_name>/test_estimator.py`, `tests/<package_name>/test_schema.py`, `tests/<package_name>/tasks/test_train_model.py`, and `tests/webapp/test_app.py` all exist, and no `test_estimator.py`, `test_schema.py`, `test_app.py`, or `test_train_model.py` exists directly under `tests/`
