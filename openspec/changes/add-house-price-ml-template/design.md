## Context

`templates/python-project/` (pinned `_min_copier_version: 9.0.0`) is the only existing template source, and generates a project into `<dest>/<package_name>/`. `templates/ml` is meant to be run a second time, directly against that already-generated project directory, to layer ML-specific files on top — not to generate a standalone project of its own. The reference implementation this change is modeled on (`/Users/Ragrawa/tmp/test_rj12/pipelines/house_price/`) trains on data pulled from BigQuery and serves via a Vertex AI custom container reading the model from GCS; this template must instead be fully local (no cloud dependency at train/serve time), per the request. See proposal.md - Why/What Changes for the two-command workflow this design implements.

## Goals / Non-Goals

**Goals:**
- `templates/ml` must generate cleanly into a directory that already contains a full python-project-generated tree, adding only new files and never re-templating or colliding with a file that already exists.
- `package_name` must be derivable from the destination path alone, with no `--data` flag needed on the `templates/ml` invocation.
- Runtime dependencies must land in the existing `pyproject.toml`/`uv.lock` without `templates/ml` shipping its own copy of that file.
- Training and serving must have zero cloud/network dependency at train-time and Docker-build-time (network is fine at `templates/ml` generation time, for the dependency-install task).

**Non-Goals:**
- Cloud deployment targets (Vertex AI, GCS, BigQuery) — explicitly out of scope; this template is local-filesystem-and-Docker only.
- Making `templates/ml` usable as a standalone template that generates a full project by itself — it is only ever run against an existing python-project-generated destination.
- Automated retraining/CI for the generated project's model — training is a manual step the developer runs before building the Docker image.

## Decisions

**1. `templates/ml` is an additive overlay template, run against an already-generated project directory.**
The developer runs two commands against the same destination:
```
uv tool run copier copy templates/python-project <dest> --trust --data package_name=house_price --data python_version=3.12
uv tool run copier copy templates/ml <dest>/house_price --trust
```
`templates/ml`'s content therefore maps directly onto that project's root (`templates/ml/src/{{ package_name }}/estimator.py.jinja` → `<dest>/house_price/src/house_price/estimator.py`), with **no** `{{ package_name }}/` wrapper folder in the template tree, unlike `templates/python-project` (which needs the wrapper because it creates the package-name folder itself). Alternative considered (and previously chosen, now superseded): a fully standalone, self-contained `templates/ml` tree that duplicates python-project's conventions — rejected once the actual usage pattern was clarified: the user always runs `ml` on top of an existing python-project output, so duplicating files that already exist there would create file-collision prompts (or silent overwrites) instead of a clean overlay.

**2. `templates/ml` ships only files that do not already exist in a python-project-generated tree.**
Out of scope for `templates/ml`: `pyproject.toml`'s packaging boilerplate, `ruff.toml`, `pyrightconfig.json`, `pytest.ini`, `.coveragerc`, `poe_tasks.toml`, `README.md`, `AGENTS.md`, `.gitignore`, `src/<package_name>/__init__.py`, `py.typed`, `tests/__init__.py`, and the `.python-version` pin. `templates/ml` only contributes: `src/<package_name>/estimator.py`, `src/<package_name>/tasks/{__init__.py, train_model.py}`, a bundled sample dataset, `webapp/app.py`, `docker/{Dockerfile, .dockerignore}`, and new test files for the added modules (distinct filenames from the base template's `tests/test_placeholder.py`, so no collision). This means `templates/ml` never needs `--overwrite`/`--defaults` handling for pre-existing files, and a fresh `copier copy templates/ml <dest>` run has nothing to conflict with.

**3. `package_name` is computed from the destination path; no `python_version` question at all.**
`templates/ml/copier.yml`'s only question is `package_name`, with `default: "{{ _copier_conf.dst_path.name }}"` and `when: false`, so it resolves silently from the destination folder name (`house_price` in the example above) and is never prompted — matching the `--data`-flag-free second command. There is no `python_version` question: nothing in `templates/ml` renders per-Python-version content or needs to know it (the `uv add` task in Decision 5 works against whatever environment python-project already pinned). Confirmed against Copier 9.18.1 (see task 1.1): `_copier_conf.dst_path.name` is readable from a question's `default:` expression and resolves to the destination folder's own name.

**4. Both templates store their answers under a hidden `.answers/` directory, each with its own filename.**
`templates/python-project/copier.yml` sets `_answers_file: .answers/.python_project.yml` (moved off Copier's default `.copier-answers.yml` at the project root), and `templates/ml/copier.yml` sets `_answers_file: .answers/.ml.yml`. This keeps every template's answer record in one hidden, discoverable location instead of scattering root-level dotfiles, and guarantees `templates/ml` never overwrites python-project's answers (or vice versa), keeping `copier update` independently trackable per template. This changes `templates/python-project`'s already-shipped output, which is normally the trigger for a `_migrations` entry per `openspec/project.md`'s compatibility rule — this is the one piece of this change that touches the existing `template-generation` capability rather than only the new `ml` capability. No entry was actually needed here, though: see Migration Plan for why (the template never wrote an answers file before this change, so there is nothing for a migration to relocate).

**Verified findings (spiked against Copier 9.18.1, then confirmed against this repo's real template):**
1. Setting `_answers_file` alone does not make Copier write an answers file at all — `templates/python-project` currently ships no answers file whatsoever, because nothing in the template renders to that path. Copier only writes the answers file when the template contains a physical file whose *rendered destination path* equals `_copier_conf.answers_file`; the canonical way to get this is a file literally named `{{ _copier_conf.answers_file }}.jinja` with content `{{ _copier_answers|to_nice_yaml }}`.
2. `_answers_file` is always resolved **relative to the raw destination path passed on the command line** (`dst_path`), never relative to wherever the boilerplate file physically sits inside the template's own directory tree. Since `templates/python-project`'s real content lives under a `{{ package_name }}/` wrapper folder (from the separately-applied `wrap-template-in-project-name-dir` change) while `copier copy templates/python-project <dest>` is invoked with `<dest>` as the *parent* of that folder, a plain `_answers_file: .answers/.python_project.yml` places the file at `<dest>/.answers/.python_project.yml` — a sibling of the generated `<package_name>/` folder, not inside it. Confirmed by spiking both placements side by side. **Fix:** `_answers_file` must itself embed the `{{ package_name }}` prefix — `_answers_file: "{{ package_name }}/.answers/.python_project.yml"` — and the boilerplate `{{ _copier_conf.answers_file }}.jinja` file must live at the **template root** (alongside `copier.yml`), *not* nested inside `{{ package_name }}/`. Confirmed this combination produces `<dest>/<package_name>/.answers/.python_project.yml` as intended.

`templates/ml` has no such wrapper folder (Decision 1: its content maps directly onto the project root), so its own `_answers_file: .answers/.ml.yml` and its `{{ _copier_conf.answers_file }}.jinja` boilerplate both stay unprefixed at its template root.

**5. Refuse to run against a destination that wasn't generated by `templates/python-project`, via a `_tasks` precondition check.**
Verified against Copier 9.18.1: a question's `validator:` does not run at all when the question has `when: false` (confirmed by spiking both cases — the invalid destination generated successfully with no error). Even without `when: false`, a `validator:`'s `_copier_conf.dst_path` is a `PurePosixPath` with no filesystem access (`.exists()` raises `AttributeError`), so a question validator cannot check the destination's contents. A template-bundled custom Jinja extension (`_jinja_extensions`) also isn't viable: Copier requires such extensions to be pre-installed in Copier's own environment ("Make sure to install these extensions alongside Copier itself"), not something the template can ship and have work standalone — that would break the self-contained, `uv tool run copier copy templates/ml <dest> --trust`-only workflow. The one mechanism that reliably works is a `_tasks` shell command: the **first** entry in `templates/ml`'s `_tasks` list checks `test -f .answers/.python_project.yml`, and if it's missing, prints a clear message to stderr and exits 1 — Copier reports the failed task and stops, so the subsequent `uv add` task never runs. Confirmed by spiking both the pass and fail cases against real Copier 9.18.1. `.answers/.python_project.yml` (from Decision 4) is the marker, since it's a stronger signal of "generated by `templates/python-project`" than a generic `pyproject.toml`.

**6. Dependency injection via `uv add`, not a duplicated `pyproject.toml`.**
`templates/ml/copier.yml` declares a `_tasks` entry: `uv add scikit-learn pandas numpy pydantic fastapi uvicorn`, run inside the destination after file rendering. `uv add` edits the existing `pyproject.toml` and `uv.lock` in place (TOML-safe, preserves the rest of the file), producing the same net result as hand-editing the file with none of the added complexity. Alternative considered: a bundled script using `tomlkit` to programmatically inject the dependency entries — rejected because it still needs its own dependency resolved before it can run (e.g. `uv run --with tomlkit ...`, which hits the network anyway), and would still require a separate `uv lock`/`uv sync` step afterward to keep the lockfile in sync — strictly more moving parts than `uv add` doing both in one step. `--trust` is required on the `templates/ml` invocation because of this task.

**7. Model artifact path and Docker build/run split.**
`train_model.py` defaults to writing `models/model.pkl` (relative to the project root; not added to `.gitignore` by `templates/ml`, since `templates/ml` doesn't own that file — see Risks). The Dockerfile does **not** train inside the image; it expects `models/model.pkl` to already exist in the build context (the developer runs the training task locally first, matching "you can modify train_house_model.py to train and save the model in a local file system" from the request, and "loads this model during deployment time" for the container).

**8. FastAPI app: `/health` and `/predict` only, no Vertex-specific routes.**
The reference `serve_app.py` includes a `/v1/endpoints/{endpoint_id}/deployedModels/{deployed_model_id}` route solely for Vertex AI's readiness probe convention. Since this template targets a generic Docker container (not Vertex custom containers), that route is dropped; only `/health` and `/predict` are generated.

**9. Docker layout: `webapp/` stays outside the installable package; multi-stage `uv` build.**
Per the requested folder structure, `webapp/app.py` is a sibling of `src/`, not inside `src/<package_name>/`. The Dockerfile copies the whole project tree (including `webapp/` and the pre-built `models/model.pkl`), runs `uv sync` to install the package and its dependencies, and starts the server with the project root as the working directory so `webapp.app:app` resolves alongside the installed `<package_name>` package: `CMD ["uv", "run", "uvicorn", "webapp.app:app", "--host", "0.0.0.0", "--port", "8080"]`. A builder stage installs dependencies and builds the wheel; the runtime stage copies only the installed environment, `webapp/`, and `models/`, keeping the final image free of build tooling.

## Migration Plan

No `_migrations` entry is needed. The original plan was a version-gated entry that would move a pre-existing root-level `.copier-answers.yml` to `.answers/.python_project.yml` on `copier update`, but implementation surfaced that this premise doesn't hold: `templates/python-project` never wrote *any* answers file before this change (confirmed via `git show 43f6de1:templates/python-project/copier.yml` — no `_answers_file`, and no `{{ _copier_conf.answers_file }}.jinja` boilerplate anywhere in that commit's tree; also reconfirmed with a standalone spike template of the same shape, which produced no `.copier-answers.yml` at all). Since Copier only ever writes an answers file when the template contains a physical file whose rendered destination matches `_copier_conf.answers_file` (see Decision 4), and no such file existed pre-change, no project generated by the old template can have a `.copier-answers.yml` to relocate. `templates/python-project/copier.yml` keeps `_migrations: []` with a comment recording this finding, instead of shipping a permanently-inert `mv ... || true` entry for a scenario that cannot occur. No migration is needed for `templates/ml` either, since it is new — there is no pre-existing `.copier-answers.ml.yml` in the wild to relocate.

**Verified constraint (spiked against Copier 9.18.1, reading `copier/_template.py`), kept for any future migration this template may need:** `Template.migration_tasks` never runs *any* migration — version-gated or not — unless **both** the subproject's previously-recorded template version and the current template's version are non-empty (`if not (self.version and from_template.version): return []`). Copier derives a template's "version" from a git tag (PEP 440-parsed) on the commit the template was copied/updated from; a plain commit hash is not a version. Confirmed in a scratch spike: tagging the template `v1.0.0` then `v1.1.0` and running `copier update` from a `v1.0.0`-generated, git-tracked destination correctly ran a migration entry. **Consequence for this repository**: it currently has no git tags at all, so any `_migrations` entry added here would not run against any real `copier update` until this repository starts tagging releases of its template source — a future migration's verification would need to exercise a temporary git-tagged copy of the template, not this repository's own untagged history.

## Risks / Trade-offs

- [`.gitignore` doesn't get a `models/` entry] → Since `templates/ml` doesn't own `.gitignore` (Decision 2), it can't safely append to it without risking duplicate lines on repeated runs. Mitigation: document in the training-task's generated docstring/README note that `models/` should be gitignored manually; not automated.
- [Two-command workflow instead of one] → A developer must remember to run `templates/python-project` first and point `templates/ml` at its output. Mitigation: Decision 5's `_tasks` precondition check makes running `templates/ml` against the wrong destination fail loudly with a clear message, instead of failing later and more confusingly inside the `uv add` step (or silently drifting).
- [Precondition check runs after files are already rendered] → Copier always renders every templated file before running any `_tasks`, so a destination missing `.answers/.python_project.yml` still ends up with `templates/ml`'s new files written into it before the check fails and stops the run. Mitigation: this is a Copier-wide ordering constraint, not something `templates/ml` can avoid; document that a failed `templates/ml` run should be cleaned up via `git status` / `git checkout -- .` (the destination is expected to already be a version-controlled project from the `templates/python-project` run, or in the invalid case, whatever version control the developer has there).
- [Bundled static dataset] → Doesn't reflect real-world/updated data. Mitigation: document in the generated project's docs how to point `train_model.py` at a different data source.
- [Model baked into the Docker image rather than mounted] → Retraining requires an image rebuild, and the image is larger than a volume-mount approach. Mitigation: acceptable for this template's local-deploy scope; document the bind-mount alternative as a follow-up option.
