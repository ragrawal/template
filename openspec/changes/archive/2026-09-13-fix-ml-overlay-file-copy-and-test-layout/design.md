## Context

See proposal.md - Why. Two independent root causes were confirmed by reproducing both bugs against the current `templates/ml/copier.yml` with `uv tool run copier` (the same invocation the existing `tests/bdd/ml_overlay_test` suite uses):

- `package_name` defaults to `{{ _copier_conf.dst_path.name }}`. `_copier_conf.dst_path` is a `pathlib.PurePosixPath` (no filesystem I/O methods - confirmed `.exists()`/`.absolute()`/`.resolve()` all raise `AttributeError` when called from a question default/validator). When the destination argument on the command line is `.`, `PurePosixPath(".").name == ""`. Copier's convention is to skip rendering any file whose path contains an empty rendered segment, so every file under `src/{{ package_name }}/` (`estimator.py`, `schema.py`, `tasks/`) silently disappears while everything else (which doesn't path through `{{ package_name }}`) renders normally. This is exactly what happens when a user does `cd <project> && copier copy .../templates/ml . --trust`, which is a natural thing to type even though the template's own docstring recommends `copier copy .../templates/ml <dest>/<package_name> --trust`.
- Copier's render pipeline always writes every templated file to disk before running `_tasks` (confirmed: `--pretend` output lists every file that would be created before any task runs). `_tasks` entry 1 (`test -f .answers/.python_project.yml || ...`) therefore can only detect and report an invalid destination *after* every ML overlay file has already been written there.
- Pure-Jinja question `validator:` expressions run during Copier's ask phase, strictly before any file is rendered (confirmed: a validator raising during `get_default()` leaves the destination directory empty) - but only when the question is actually *asked*. `package_name` here has `when: false`, which is required to keep the documented flagless, non-interactive invocation (`copier copy templates/ml <dest>/<package_name> --trust`, no `--defaults`) working: removing `when: false` to make the question askable (and its validator run) breaks that invocation with `Interactive session required: Use --defaults and/or --data/--data-file` whenever stdin isn't a TTY (confirmed by running with `< /dev/null`, matching how the BDD suite and real automated usage invoke Copier). So a validator on `package_name` can never fire for this template's real invocations, and detecting the empty-name case has to happen elsewhere. Separately, validators have no filesystem access beyond attribute access on the `PurePosixPath` objects Copier hands them - checking whether a *destination file* exists would require a custom Jinja extension, and Copier's `jinja_extensions` mechanism requires that extension to be an independently *installed* Python package alongside Copier (confirmed: referencing an in-template module by relative or dotted path fails with `No module named ...`). Adding an installable dependency just to run a pre-render existence check conflicts with this template's "single `copier copy` command, no setup" design, so this option is rejected too.

## Goals / Non-Goals

**Goals:**
- Fail loudly, before rendering, when `package_name` cannot be derived from the destination - instead of silently omitting files.
- Ensure a destination that fails the "generated by `templates/python-project`" prerequisite check ends up with none of `templates/ml`'s files on disk, and that this check still runs before the `uv add` dependency-install tasks.
- Reorganize the overlay's own test files to mirror the source/webapp layout, and update the regression suite to match.

**Non-Goals:**
- Does not change `templates/python-project` or its specs.
- Does not attempt a true pre-render filesystem check for the prerequisite marker file (rejected above as requiring an extra installed dependency); the chosen approach is fail-and-cleanup instead.
- Does not change the recommended invocation (`copier copy .../templates/ml <dest>/<package_name> --trust`) or add interactive prompting for `package_name` in the common case - the fix only closes the silent-failure gap for the case where the derived name is empty.

## Decisions

**1. Empty `package_name` → post-render `_tasks` detection + cleanup, not a validator.**
There is no supported way to resolve `.` to the real current-directory name from a pure-Jinja question default (`PurePosixPath` has no `resolve()`/`absolute()`, and Copier exposes no cwd/env global). A `validator:` on the `package_name` question was tried first, but it never fires: the question has `when: false` (required to keep the documented flagless, non-interactive invocation working - see Context), and Copier only runs a question's validator when the question is actually asked. Making the question askable to enable the validator breaks the flagless invocation outright whenever stdin isn't a TTY. Instead, this is detected as a second `_tasks` entry, alongside the prerequisite check in Decision 2: `pkg="$(basename "$PWD")"` resolves the real destination directory name from the shell (bash always sees an absolute, resolved cwd, unlike Jinja's `_copier_conf.dst_path`), and a missing `src/$pkg/estimator.py` is treated as proof that `package_name` resolved to an empty string during rendering (the same empty-path-segment failure mode silently drops `estimator.py`, `schema.py`, and everything under `tasks/`, so checking for one of them catches all three). On this condition, the task prints a clear message telling the user to re-run against an explicit `<dest>/<package_name>` path or pass `--data package_name=<name>`, deletes every path this template rendered, and exits non-zero - reusing the same cleanup mechanism as Decision 2 rather than a separate one.

**2. Prerequisite check: fail-fast task + explicit cleanup, not a pre-render hook.**
Since no pre-render mechanism can check for `.answers/.python_project.yml` in the destination without an installed extension (rejected in Context), keep the marker check as `_tasks` entry 1 (it already runs before the `uv add` tasks), but change it so that on failure it removes the exact set of paths this template renders (`src/<package_name>/estimator.py`, `src/<package_name>/tasks/`, `webapp/`, `docker/`, `docs/ML_README.md`, `.dockerignore`, `.answers/.ml.yml`, and any test paths from Decision 3) before exiting non-zero. The task becomes a single shell command: check the marker, and on failure `rm -rf` the known ML-overlay paths then exit 1. Because these paths are a fixed, fully-known list (this template never writes anywhere else), deleting them by name is safe and doesn't risk touching files `templates/python-project` created. `_tasks` entry 2 (Decision 1) follows immediately after, using an identical `cleanup()` function, before the `uv add` dependency-install tasks.

**3. Test layout: move files at template-authoring time, not via a rendering trick.**
Move `templates/ml/tests/test_estimator.py.jinja` and `test_schema.py.jinja` to `templates/ml/tests/{{ package_name }}/`, move `test_train_model.py.jinja` to `templates/ml/tests/{{ package_name }}/tasks/`, and move `test_app.py.jinja` to `templates/ml/tests/webapp/`. This is a plain source-tree reorganization (Copier maps template paths onto the destination directly), requiring corresponding import-path fixes only if the moved tests import fixtures via relative paths (verify during implementation).

## Risks / Trade-offs

- [The fail-and-cleanup approach still writes files transiently to disk before deleting them, so a process killed mid-run between render and cleanup could leave partial files behind] → Acceptable: this is strictly better than the current behavior (which leaves the same files behind permanently on any failure), and matches how the existing `_tasks`-based check already behaves for other failure modes.
- [The cleanup step's hardcoded path list must stay in sync with whatever `templates/ml` adds] → Mitigate by deriving the cleanup list from the same set of top-level paths documented in the `ml` spec's file lists, and covering it with the BDD regression test so drift is caught.
- [Moving test files could break relative imports or fixture discovery within the moved `.jinja` test files] → Verify each moved test still passes after the move (existing `tests/bdd/ml_overlay_test` scenario already runs `uv run poe check`, which includes pytest, against a freshly generated project).
