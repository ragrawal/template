## Why

The `templates/python-project` template scaffolds a generic installable Python package, but every ML project that trains a model and serves it needs to re-solve the same problem: where to put the estimator, how to train and persist a model artifact, and how to wrap it in a container-servable web API. A second, additive Copier template lets a developer layer a ready-to-train, ready-to-deploy house-price prediction project onto a project they've already generated from `templates/python-project`, instead of hand-assembling training code, a FastAPI serving app, and a Dockerfile each time.

## What Changes

- Add a new Copier template source at `templates/ml/` that is run a **second time**, against the output directory a developer already generated from `templates/python-project`, and adds ML-specific files into that existing project rather than generating a new project from scratch:
  ```
  uv tool run copier copy templates/python-project <dest> --trust --data package_name=house_price --data python_version=3.12
  uv tool run copier copy templates/ml <dest>/house_price --trust
  ```
- `templates/ml` ships only files that don't already exist in a python-project-generated tree: `src/<package_name>/estimator.py`, `src/<package_name>/tasks/train_model.py` (+ `__init__.py`), a bundled sample dataset, `webapp/app.py`, `docker/Dockerfile`, `docker/.dockerignore`, and new test files for the added modules. It does NOT ship `pyproject.toml`, per-tool configs (`ruff.toml`, `pyrightconfig.json`, `pytest.ini`, `.coveragerc`, `poe_tasks.toml`), `README.md`, `AGENTS.md`, `.gitignore`, or `src/<package_name>/__init__.py`/`py.typed` — those already exist from the python-project run and are left untouched.
- `templates/ml`'s only answer-schema question is `package_name`, and it is never prompted: its `default` is computed from the destination directory's own name (`{{ _copier_conf.dst_path.name }}`) and `when: false`, so `copier copy templates/ml <dest>/house_price --trust` needs no `--data` flags at all. There is no `python_version` question — nothing in `templates/ml` needs it.
- Both templates store their Copier answers under a hidden `.answers/` directory instead of loose root-level dotfiles: `templates/python-project` writes `.answers/.python_project.yml` (changed from Copier's default `.copier-answers.yml`, with a `_migrations` entry so `copier update` relocates existing projects' answers files), and `templates/ml` writes `.answers/.ml.yml`. This keeps `copier update` independently trackable per template and avoids `templates/ml` ever overwriting the base template's answers.
- A `templates/ml` post-generation `_tasks` step runs `uv add scikit-learn pandas numpy pydantic fastapi uvicorn` inside the destination, letting `uv` merge the runtime dependencies into the existing `pyproject.toml` and `uv.lock` in place, instead of `templates/ml` shipping its own `pyproject.toml`.
- Running `templates/ml` against a destination that was not already generated by `templates/python-project` (no `.answers/.python_project.yml` present) fails loudly with a clear error, instead of failing confusingly later or succeeding into a broken state.
- Generated `estimator.py` ships a `HousePredictionModel` (`fit`/`transform`/`predict`) adapted from the reference implementation, over a California-housing-shaped feature set.
- Generated `tasks/train_model.py` loads a bundled local dataset (no BigQuery/GCP dependency), trains `HousePredictionModel`, evaluates it (RMSE/R2), and pickles the trained model to a local filesystem path (default `models/model.pkl`).
- Generated `webapp/app.py` loads the pickled model and estimator classes from the local filesystem at startup and exposes `/health` and `/predict` endpoints (Vertex-AI-specific routes from the reference app are dropped since this template targets a plain Docker deployment, not Vertex custom containers).
- Generated `docker/Dockerfile` (multi-stage, `uv`-based) and `docker/.dockerignore` build the package, expect a pre-trained `models/model.pkl` artifact in the build context, and run the FastAPI app under `uvicorn`.

## Capabilities

### New Capabilities
- `ml`: Copier template source that overlays a house-price ML training pipeline, a local pickled model artifact, a FastAPI serving app, and Docker packaging onto a project already generated from `templates/python-project`.

### Modified Capabilities
- `template-generation`: `templates/python-project` now stores its Copier answers file at `.answers/.python_project.yml` instead of the default `.copier-answers.yml` at the project root, with a `_migrations` entry so `copier update` relocates existing projects' answers files.

## Impact

- New directory tree: `templates/ml/` (copier.yml + templated content, mapped directly onto a project root — no `{{ package_name }}/` wrapper folder, since the destination is already that project root).
- `templates/python-project/copier.yml` gains an `_answers_file` setting and a `_migrations` entry; no other files in `templates/python-project/` change.
- This repository's own regression-test suite (`tests/bdd/`) will need a companion scenario (tracked in tasks.md) that chains both `copier copy` invocations against the same destination and exercises the resulting project.
- Requires `uv` and network access at `templates/ml` generation time (for the `uv add` task), consistent with the rest of this repo's `uv`-based tooling; no cloud dependency at train-time or Docker-build-time.
- No production/runtime systems affected outside the generated project; the generated Dockerfile is new build/deploy tooling delivered to whoever generates a project from this template.
