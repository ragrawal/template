## Context

`templates/python-project/copier.yml` currently defines eight questions. Six (`project_name`, `description`, `author_name`, `author_email`, `license`, `coverage_threshold`) are being dropped entirely per the user's decisions (see proposal.md - Why): no LICENSE file, author name kept empty rather than removed from `pyproject.toml`, and `project_name` becomes the literal `package_name` value. `_migrations` in `copier.yml` already exists as an (empty) list, so `copier update` on a project generated by an older version of this template needs a migration entry to avoid erroring on now-unknown answer keys.

## Goals / Non-Goals

**Goals:**
- Shrink `copier.yml` to two questions: `package_name`, `python_version`.
- Keep every generated file that referenced a removed answer producing valid output (no broken Jinja, no dangling references).
- Keep `copier update` working for projects generated under the old, eight-question schema.

**Non-Goals:**
- Reintroducing any of the six removed answers as hidden/computed Copier variables (`when: false`) - the proposal's decisions (no LICENSE, empty author name, literal `project_name`) are simple enough to hardcode directly in the affected templates, which is less machinery than keeping six unused variables alive.
- Changing anything about `package_name`'s or `python_version`'s existing validators, choices, or defaults.

## Decisions

- **Hardcode instead of computing hidden variables.** Rather than keeping `project_name`, `description`, `author_name`, `license`, `coverage_threshold` as Copier variables with `when: false` and a fixed `default:`, remove the keys from `copier.yml` entirely and edit each consuming template directly (e.g. `.coveragerc`'s threshold becomes the literal integer `80`; `AGENTS.md.jinja` and `src/{{ package_name }}/__init__.py.jinja` reference `package_name` instead of `project_name`/`description`). Fewer moving parts, and it matches how `templates/python-project/template/LICENSE.jinja` is handled (deleted outright rather than kept as a permanently-`None`-rendering template).
- **`pyproject.toml`'s `authors` field is dropped entirely.** The user's initial preference was to keep `authors` with an empty `name` and no `email`, but hatchling's build-backend validation rejects an author entry that has neither a non-empty `name` nor an `email` (`uv sync` fails with "Author #1 of field `project.authors` must specify either `name` or `email`"), discovered by actually generating and syncing a project. Since `authors` is optional under PEP 621, dropping the key entirely is the only option that satisfies "no author info collected" without breaking the build.
- **`_migrations` drops the six removed keys and does not synthesize a `project_name`.** A `copier update` on an old project supplies the previously-answered `project_name`, `description`, `author_name`, `author_email`, `license`, `coverage_threshold` values from `.copier-answers.yml`; since none of these are declared in the new `copier.yml`, Copier's normal update flow simply stops persisting them going forward (no explicit `before`/`after` transform script is needed - a migration entry is only required if we want a hook to run, e.g. to warn the user). Add a version-gated no-op migration entry now (per the existing `template-generation` compatibility requirement) so the change itself is recorded, even though no data transform is necessary.

## Risks / Trade-offs

- [Downstream projects lose the ability to re-run `copier update` and get an updated `LICENSE`/description/author metadata for free] → Acceptable per the user's explicit decision; these files, once generated, are no longer template-managed and are expected to be edited directly in the downstream repo.
- [A future contributor might want per-project descriptions or licenses back] → Re-adding a question later is backward compatible (new key with a `default:`), so this isn't a one-way door.

## Migration Plan

1. Update `templates/python-project/copier.yml`: remove the six question blocks; add a `_migrations` entry version-gating the schema change.
2. Update the consuming templates (`pyproject.toml.jinja`, `README.md.jinja`, `AGENTS.md.jinja`, `src/{{ package_name }}/__init__.py.jinja`) to hardcode the fixed behavior; delete `LICENSE.jinja`.
3. Update `tests/bdd/python_project_test/python_project_test.feature` (and any fixture under `tests/bdd/actions/`) to stop passing `-d` for removed fields and to assert the new fixed output (no `LICENSE`, empty author name, `package_name`-derived heading, fixed `80`% coverage threshold); drop the out-of-range `coverage_threshold` scenario.
4. Run `uv run pytest` in this repo (its actual CI check; this repo has no `poe check` task of its own) to confirm the regression suite passes against the updated template.

No rollback beyond `git revert` is needed since this only affects template source, not already-generated downstream projects.
